name: core-clocks
description: Use when debugging how this plugin interacts with **PWQ** (Parallel Warming Quantum — the intra-machine, across-cores barrier inside ONE simulated machine, owned by parallel-qemu). Specifically when "the snapshot isn't firing" / "the quantum callback isn't being called" / "per-core vtime is drifting in checkpoints" / "snapshots are landing at the wrong virtual time". The headline: WormCache is NOT part of PWQ enforcement — it only *registers* `quantum_checking_callback` (in `src/chronic/snapshot.rs`) via `qemu_plugin_register_periodic_check_cb`, and QEMU itself invokes it (from the PWQ barrier leader in parallel mode, from the RR loop in non-parallel mode). Per-core `vts` is set by parallel-qemu's `cpu_virtual_time[]` machinery, not by this plugin. Policy/mechanism split: this plugin is the policy ("snapshot now?"), parallel-qemu's PWQ machinery is the mechanism. The `check_period` cadence governs how often QEMU asks. **Does NOT cover MNQ (Multi-Node Quantum) — the across-machines drain that lands distributed snapshots after `savevm_cb` fires; use the `multi-node` skill for that, including the policy/mechanism split at the cross-machine layer.** TRIGGER when the user mentions PWQ / `quantum_checking_callback` / `pf_periodic_check_cb` / `qemu_plugin_register_periodic_check_cb` / `savevm_cb` timing within ONE machine / per-core vtime in checkpoints / "why is the snapshot landing at virtual time X" / interaction between WormCache and the barrier or quantum inside one machine. SKIP for MNQ / cross-machine drain / `qemu-pdes/` / WWT / unrelated plugin questions (modes, cache hierarchy, checkpoint format, NUMA in cache code).
